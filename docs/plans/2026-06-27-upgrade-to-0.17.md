## ⚠️ Correction to the handoff's "gutted subsystems" framing

The handoff described this upgrade as an **architecture reconciliation** where
the fork "gutted" `computer_use`, `async_delegation`, `blueprints`,
`clarify_gateway`, etc., and the plan must decide per-subsystem whether to
re-adopt upstream or re-delete. **This is a misread of the fork-vs-release
diff and is materially wrong.**

Evidence (verified 2026-06-27):

| File | present@v0.13 | present@v0.17 | present@fork |
|---|---|---|---|
| `tools/computer_use/tool.py` | **absent** | present | **absent** |
| `tools/async_delegation.py` | **absent** | present | **absent** |
| `tools/blueprints.py` | **absent** | present | **absent** |
| `tools/clarify_gateway.py` | **absent** | present | **absent** |
| `tools/computer_use_tool.py` | **absent** | present | **absent** |

These files did **not exist at v0.13** — they were *added by upstream after
0.13*. The fork did not excise them; it simply predates them. The `-941 / -823 /
-780` line counts in the handoff's table are an artifact of diffing `main`
(≈v0.13) against the release (v0.17): the release has the new files, the fork
doesn't. **There is nothing to "re-delete" and no architecture decision to
make.** When we rebase onto v0.17, upstream's new `computer_use/`,
`async_delegation.py`, `blueprints.py`, `clarify_gateway.py` will simply appear
as part of the new base — they are additive, not conflicting.

> **One follow-up worth noting (post-upgrade, optional):** the fork's hardening
> rationale was always *scoped replacements* (`tools/mcp_approval.py`,
> `tools/network_policy.py`) rather than deleting upstream capability.
> Upstream's newly-arrived `computer_use` / `blueprints` / `clarify_gateway` are
> *additive* subsystems the fork has never carried. They will be present after
> upgrade. If the fork owner wants them disabled, that is a **new, separate**
> hardening decision (e.g. config gate or tool-type exclusion), *not* a
> rebase resolution. Deferred to Phase 3 as an explicit evaluation item so it
> isn't smuggled in as a conflict fix.

fork's small edit** at its new location in the churned upstream file — find the
upstream equivalent of the insertion point, re-apply the fork's hunk there. We
are *not* choosing between two implementations; we are relocating ~10 small
hunks. This is the same shape as the 0.10→0.13 rebase, which succeeded with
exactly this technique.

#### The 37 `tests/tools/` failures are NOT rebase regressions — verified 2026-06-27
Compared the worktree failure set vs (a) pre-upgrade `main` v0.13.0 and (b) a
**clean upstream v0.17 worktree with zero fork commits** (throwaway
`../hermes-pure-v17`, since removed). Findings:

- The "new on upgrade" failures cluster in
  `test_cross_profile_guard`, `test_line_ending_preservation`, `test_file_tools`,
  `test_file_tools_cwd_resolution`, `test_patch_failure_tracking`,
  `test_resolve_path`, `test_voice_mode`, `test_terminal_tool` (sudo),
  `test_kanban_tools`, `test_gateway_cwd_contract`.
- **Root cause is macOS, not the fork** (reproduced on clean upstream v0.17):
  - **Sensitive-path guard vs macOS `$TMPDIR`**: v0.17's file-safety layer
    refuses writes to paths under `/private/var/folders/.../T/` (macOS's
    `pytest` tmpdir), e.g. `Refusing to write to sensitive system path:
    /private/var/folders/.../T/pytest.../lf.txt`. CI is Linux (tmpdir under
    `/tmp`), so upstream's CI is green — this is local-mac-only friction, same
    on clean v0.17 with no fork applied.
  - **`/tmp → /private/tmp` realpath**: macOS symlink resolution; tests that
    assert unresolved `/tmp/...` vs resolved `/private/tmp/...`. Environment-
    dependent (which Python/subprocess tmpdir), reproduces under both v0.13 and
    v0.17 on this machine.
  - **PulseAudio socket tests (`test_voice_mode`)**: PulseAudio is a Linux audio
    daemon; absent on macOS. Same on clean v0.17.
  - **`test_terminal_tool` sudo, `test_code_execution_modes` venv fallback**:
    miniforge/PATH drift on this host (identical failure on pre-upgrade main).
- The fork-relevant suites — `test_docker_environment`, `test_network_policy`,
  `test_mcp_approval` — **all pass**. No fork-added or fork-touched test
  regressed.
- Pre-upgrade `main` itself had **22 failed** on the same slice (different but
  overlapping env failures), so the suite was never clean on this macOS host.
  The upgrade does not make it materially worse and introduces no new
  fork-caused failures.

**Verdict: Phase 2 green for the fork's purposes.** The remaining failures
